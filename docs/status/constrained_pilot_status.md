## Open architectural decisions

- **A3-PR2b — serialize account-state validation with posted-event emission (MERGED, PR #116, 2026-08-09).** Implemented as the serialized boundary `emit_posted_journal` plus Counter-first account mutations (`update_account`/`delete_account`), pk-ordered Account row locks, frozen AccountProjection update fields, and the four touched document-order corrections (vendor-payment bill locks, receipt-allocation invoice locks, credit-note original-invoice lock, platform DRAFT recovery → visible manual-review failure). Proven by the PostgreSQL concurrency suite tests/e2e/test_account_state_serialization.py. The sole fresh-review P2 (external `account.*` event-only mutation door: an ingested account event commits at sequence N while its row-apply lags, letting a journal at N+1 validate against pre-update facts) is closed by PROHIBITION — external ingest cannot mutate account state at all; see External-Ingest-Surface-Hardening below. The subsequent fresh-review P1 (the same forbidden history through the internal path: `update_account`/`delete_account` could commit their event while the fail-soft projection drain left the Account row unmaterialized — paused bookmark, handler error, or sync disabled) is closed FAIL-CLOSED: the command reports success only after proving the exact per-event ProjectionAppliedEvent marker AND the Account-row postcondition inside its owning transaction, else the entire attempt (event, consumed sequence, marker, row change, on_commit dispatch) rolls back with a visible CommandResult failure — mutation unavailability is accepted; contradictory financial history is not. Merged; A3-PR3 (apply/replay enforcement) landed 2026-08-21 — see the A3 row.
- **Lock-Order Normalization (open; deferred availability hazards — NOT accepted financial-corruption paths).** The A3-PR2b lock-graph closure inventory found nine PRE-EXISTING opposing lock-order pairs on main that PR2b deliberately does not fix (it introduces none and removes four): JournalEntry (standalone save/post/reverse vs JournalEntryProjection under the sync drain); CompanySequence (standalone posting vs composed flows and projection JE builders); InventoryBalance / FifoLayer / StockLedgerSequenceCounter (standalone inventory commands vs composed sales/purchase/Shopify paths); ShopifyOrder (paid-stub upgrade vs handler stamp-back); ShopifyDispute (dispute-won update vs dispute-created handler); ShopifyFulfillment (4h sweep vs order-paid drain); ShopifyStore (OAuth saves vs sync_payouts); BankStatementLine (manual_match/resolve_difference vs ReconciliationProjection); JournalLine.reconciled (auto-match prepass vs projection). Consequence class: PostgreSQL may abort ONE transaction as a deadlock victim and roll it back atomically; the retry heals it — an availability/retry hazard, not a corruption path, and A3-PR2b makes no global deadlock-freedom claim. A5 must surface database deadlock/lock failures as visible retryable outcomes. This workstream becomes IMMEDIATELY active if any pilot observes a deadlock, and must complete before materially increasing per-company concurrency, shared multi-merchant database use, inventory re-enable, private beta, or GA. Accounting Kernel V1 is a natural migration point, but not the only trigger.
- **External-Ingest-Surface-Hardening (open; deferred — the `account.*` prohibition itself is ACTIVE, shipped with A3-PR2b).** The A3-PR2b correction closes the external account-mutation ordering hole by PROHIBITION: `events/ingest_policy.py` is the single definition of the reserved internal-event-type set (`account.created`, `account.updated`, `account.deleted` — the complete set of registered types whose projection mutates the Account rows feeding posted-journal validation); the runtime ingest boundary rejects them before any BusinessEvent lookup, financial lock, event emission or projection scheduling, with no financial persistence, regardless of key configuration (pre-existing rows and direct DB/admin edits cannot re-open the door; API-key authentication necessarily performs its key lookup and last_used_at touch first); `ExternalAPIKey.create_key` rejects them early as supplemental validation; an architecture meta-test pins the registered `account.*` namespace AND AccountProjection's consumed types to the reserved set, and the reserved set to registered types. Broader hardening of the generic ingest surface remains DEFERRED, without implementing now: replacing the broad registered-event surface (EVENT_DATA_CLASSES) with an explicit positive registry of externally ingestible contracts; source-system ↔ event-type compatibility; supported API-key creation/update validation and migration for existing rows; causal/materialization semantics for any future externally requested canonical-state mutation; operator-visible durable outcomes and retry handling for rejected/failed ingest. Activation triggers (any of): exposing generic ingest to third parties; onboarding another connector through generic ingest; permitting an external source to request canonical account or other command-owned state mutations; moving beyond the constrained isolated pilot contract. This deferral must NOT be used to weaken or postpone the active prohibition.
- **Inventory Books-Delta Foundation (open; blocking for inventory accounting, NOT for the constrained pilot).** The A3-PR2 root-cause assessment proved that correct inventory books amounts are a cross-workflow foundation, not per-call-site rounding — the partial raw-movement-quantization implementation was removed from PR #113 rather than presented as correct. Required scope: one provider-neutral inventory movement plan/apply boundary; the old-to-new STORED-books delta as the canonical books movement (GL inventory amount = `StockLedgerEntry.value_delta` = `InventoryBalance.stock_value` delta = inventory-event books movement); weighted-average costing; FIFO preview/apply and residue/shortfall semantics; `StockLedgerEntry` explicit-zero behavior; inventory adjustments and opening balances; sales-invoice COGS; Shopify fulfillment and refund restock; direct purchase bills; PO goods receipts versus supplier bills; GRNI/PPV policy; purchase credit notes; sales and purchase void stock effects; warehouse transfers; goods-receipt reversals; SQLite/PostgreSQL explicit-rounding parity. Until it lands it BLOCKS: re-enabling inventory accounting; onboarding any merchant relying on Nxentra inventory; any claim that inventory accounting is supported. It does NOT block the constrained Option B pilot — the pilot requires NON_STOCK items and no inventory/COGS accounting (A4 runtime gates + preflight residue detection keep those paths unreachable). Interim posture: inventory operations that cannot produce an exact current-ledger payload fail loudly at the canonical emit boundary rather than emitting unvalidated financial truth. Distinct from A3-PR2b (account-state serialization — blocks all real merchant data) and from the Precision Foundation below (global currency/precision schema decision).
- **Precision Foundation (future, pre-multi-currency).** The current two-decimal JournalLine schema and `Decimal("0.01")`/ROUND_HALF_EVEN posting quantum are the CONSTRAINED-PILOT (EGP-only) contract, not the permanent global policy. Before foreign-currency input is re-enabled, a non-EGP merchant is onboarded, multi-currency ships, or GA: decide ISO 4217 minor units, currency-aware quantization, money-field capacity/scale, quantity/unit-cost/exchange-rate/tax precision, rounding modes and accounts, calculation-vs-posting precision, display precision, and migration from the (18,2) schema. The controlled fresh-database reset may be the lowest-cost schema-widening point.
